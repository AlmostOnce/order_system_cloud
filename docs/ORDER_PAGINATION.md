## 接口

`GET /api/orders/list?status=active&limit=20`，认证身份决定user_id，不接收其他用户编号。

| 参数 | 规则 |
| --- | --- |
| status | all、pending、active、completed、cancelled，默认all；未知值拒绝 |
| limit | 默认20，范围1至50；数据层最多读取limit+1条 |
| cursor | 上一页的nextCursor字符串，首屏不传；必须为本人的合法Long订单编号 |

active由服务端映射为已支付、制作中、待取货；其他状态分别为待支付、已完成、已取消。响应data为`{"items":[],"nextCursor":null,"hasMore":false}`。有更多时nextCursor为本页末条订单编号字符串。

## 查询与边界

Controller从JWT取得用户编号，Service校验状态、条数、Long溢出及游标归属，Mapper始终包含user_id条件。按order_id倒序，后续页只取order_id小于游标的记录，顶部新增订单不改变当前向后翻页的边界。游标只要求属于本人，不要求其状态仍与筛选一致，避免状态流转后无法继续翻页；切换筛选必须从首屏开始。实时状态改变仍可能使已经加载的旧记录不再属于当前筛选，页面在顶部时，下一次通知会重查当前筛选最新一页；阅读历史期间将该通知合并延迟至返回顶部或手动下拉，不承诺跨多个请求的数据库快照。

数据库多取一条判断hasMore，不执行全量COUNT或深OFFSET；只将本页摘要转换为VO，不加载菜品明细。现有OrderWindowNameService对页内去重窗口批量查名称，一页最多50条只需一个批次，商品服务不可用沿用名称缺失降级。

前端上滑到底加载更早一页，追加按orderId去重；切换筛选、离页、账号切换使旧请求失效。追加失败保留列表与游标，下一次触底重试；下拉失败保留列表，成功则重置到最新一页。后台通知不会在阅读历史时删除追加页，回到顶部才处理一次延迟刷新。加载中、刷新中与已到底禁止重复追加。新页返回的服务端时间只校准统一时钟偏移，不重新起算前面订单的十五分钟倒计时。
