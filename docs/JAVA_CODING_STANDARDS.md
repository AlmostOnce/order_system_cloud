# Java 编码规范（项目执行版）

本项目后续 Java 代码以《阿里巴巴 Java 开发手册》的核心原则为基础，并结合 Spring Boot、Spring Cloud Alibaba、MyBatis-Plus 微服务项目特点执行。

> 本文是项目内的可执行摘要，不替代原规范全文。发生冲突时，优先遵循项目现有架构约定、编译器检查和团队明确决定。

## 1. 基本格式

- 使用 4 个空格缩进，禁止使用 Tab 缩进。
- Java 文件使用 UTF-8 编码，类名、方法名和变量名使用英文语义命名。
- 包名全部使用小写，例如 `com.hbue.order.controller`。
- 类名、接口名、枚举名使用大驼峰，例如 `OrderController`、`OrderStatus`。
- 方法名、参数名、局部变量使用小驼峰，例如 `findByOrderId`、`orderId`。
- 常量使用全大写加下划线，例如 `MAX_RETRY_COUNT`。
- 一行代码不超过 120 个字符；复杂表达式拆分为多行。
- 左大括号不单独占行；类、方法和逻辑代码之间保留适当空行。
- 删除无意义的注释、空方法、无用 import 和调试代码。

## 1.1 注释规范

### 阿里巴巴规范要求

- 类、类属性和类方法的注释使用 `/** */` Javadoc 格式。
- 抽象方法和接口方法必须写 Javadoc，并说明用途、参数、返回值和可能抛出的异常。
- 每个类必须包含创建者和创建日期信息，例如 `@author` 和 `@date`。
- 方法内部的单行注释使用 `//`，并放在被注释代码的上一行。
- 方法内部的多行注释可以使用 `/* */`，并保持与代码对齐。
- 枚举类型的每个枚举项都必须有注释。
- 注释应描述业务意图、设计原因或重要约束，不能写没有解释价值的注释。
- 注释必须随着代码同步维护，过期注释必须及时删除或修改。

### 本项目额外要求

- 注释统一使用中文；技术名词、类名、方法名和协议名保留英文。
- 为保持代码风格统一，方法内部的普通逻辑说明优先使用 `//`；复杂多行说明仍可使用 `/* */`。
- 复杂算法、并发控制、幂等处理、状态流转和跨服务补偿逻辑必须写明设计原因。
- 后续输出的项目代码同时满足阿里巴巴规范和本项目额外要求。

## 2. 命名与设计

- 命名必须表达真实业务含义，禁止使用 `data`、`info`、`obj`、`tmp` 等无语义名称。
- 布尔字段使用 `is`、`has`、`can` 或 `enable` 等清晰前缀。
- 不使用拼音命名业务类、字段或方法。
- 不使用魔法值。状态、类型和权限等固定值优先使用枚举或常量。
- `BigDecimal` 不使用 `equals` 判断数值相等，使用 `compareTo`。
- 金额统一使用 `BigDecimal`，禁止使用 `float` 或 `double` 保存金额。
- POJO、DTO、VO 等对象不在字段声明处设置无必要的默认值。
- POJO 应提供清晰的 `toString` 实现，便于排查运行时问题。
- 重写 `equals` 时必须同时正确重写 `hashCode`。
- 不把可变对象、线程不安全对象或业务状态定义为静态共享变量。
- 方法只完成一个主要职责，过长方法应拆分为有明确含义的私有方法。

## 2.1 POJO 类型与命名

- `DO`（Data Object）表示数据库持久化对象，负责表字段映射，例如 `OrderDO`、`DishDO`。
- `DTO`（Data Transfer Object）表示服务之间或接口层的数据传输对象，例如 `OrderCreateReqDTO`、`OrderRespDTO`。
- `VO`（View Object）表示面向前端或调用方的展示对象，例如 `OrderDetailVO`。
- `BO`（Business Object）表示业务处理对象，仅在需要封装复杂业务数据或业务流程时使用，例如 `OrderCreateBO`。
- `PO`（Persistent Object）是持久化对象的另一种命名。当前项目统一使用 `DO`，不同时创建 `PO` 和 `DO` 表示同一张表。
- `AO`（Application Object）只在确有应用层编排对象时使用，不为凑分层而创建。
- 数据库表映射类必须使用 `DO` 后缀；MyBatis-Plus 的 `@TableName` 和 `@TableId` 放在 DO 上。
- Controller 不得直接返回 DO；接口返回必须使用 VO 或明确的响应 DTO。
- Controller 接收复杂请求时使用请求 DTO，不直接使用 DO 接收前端参数。
- 请求 DTO 和响应 VO 必须分包管理；VO 不得放在 `dto` 包下。
- 请求对象统一放在 `dto.request`，服务间传输对象可放在 `dto` 或独立的 `api` 模块。
- 面向前端的返回对象统一放在 `vo` 或 `view` 包下，例如 `order.vo.OrderDetailVO`。
- DO、DTO、VO、BO 等不同实体类型必须放在不同职责的包中，禁止混放。
- `model` 或 `domain` 包只放 DO；`dto` 包只放 DTO；`vo` 包只放 VO；`bo` 包只放 BO。
- 业务枚举统一放在 `enums` 包，异常统一放在 `exception` 包，避免与实体对象混放。
- Service 内部需要组装复杂业务数据时才使用 BO，简单查询不强行创建 BO。
- 不为了形式创建无业务意义的重复对象；类型必须有明确边界和用途。

## 3. 空值、异常与日志

- 调用可能返回空值的方法时必须明确处理空值，不能依赖偶然行为。
- 不捕获后忽略异常；禁止空的 `catch` 块。
- 不使用 `catch (Exception e)` 掩盖具体异常，除非在最外层统一兜底并保留原始异常。
- 业务失败使用项目统一的业务异常和错误码，不直接向前端暴露堆栈信息。
- 不使用 `System.out.println` 和 `e.printStackTrace()`，统一使用项目日志框架。
- 日志使用参数化写法，例如 `log.info("orderId={}", orderId)`，不要字符串拼接。
- 日志中禁止输出密码、Token、支付密码、完整身份证号等敏感信息。
- 异常日志必须包含必要的业务上下文；同一异常只在合适的边界记录一次，避免重复打印。

## 4. Spring 分层规范

```text
Controller  →  Service  →  Mapper  →  Database
                  ↓
            Feign/HTTP/MQ
```

- `Controller` 只负责参数接收、基础校验、调用 Service 和返回结果，不写业务流程。
- `Service` 负责业务编排、事务边界和业务规则。
- `Mapper` 只负责数据库访问，不调用其他服务，不写业务判断。
- 事务注解放在 Service 的业务方法上，事务范围保持尽可能小。
- Controller 不直接依赖 Mapper，不直接操作数据库。
- 接口输入输出优先使用 DTO、Command、Query 和 VO；不要直接把数据库 Entity 作为长期稳定的接口契约。
- 统一使用构造器注入，避免字段注入 `@Autowired`。
- Controller 路径、请求方法和返回结构保持清晰、稳定、符合 REST 语义。

## 5. 微服务边界

- 服务之间只能通过 Feign、HTTP 或消息通信，禁止跨服务直接访问数据库。
- 每个服务只拥有自己的表和数据写权限；开发阶段可以共用 MySQL 实例，但必须使用独立 Schema 或清晰的数据边界。
- Nacos 只负责注册发现和配置管理，业务代码不硬编码服务实例 IP。
- 服务调用使用服务名和 Spring Cloud LoadBalancer，不使用 Ribbon。
- 跨服务调用必须考虑超时、重试、幂等、降级和异常转换。
- Sentinel 规则和降级逻辑放在服务边界或网关边界，不在业务代码中到处散落限流判断。
- 不把用户密码、Nacos 密码、数据库密码和 Token 写入 Java 源码或提交到 Git。

## 6. MyBatis-Plus 与数据库

- Entity 只表达数据库映射，不把复杂业务逻辑写进 Entity。
- 表名、字段名统一使用小写下划线命名，例如 `order_id`、`created_at`。
- 主键、金额、时间、状态字段必须明确 Java 类型和数据库类型。
- 数据库字段和 Entity 字段必须保持一一对应；非同名字段显式使用 `@TableField`。
- 查询必须限制返回字段和数据范围，避免无条件查询大表。
- 批量操作必须控制批次大小，禁止在循环中逐条发起大量数据库请求。
- 更新必须带有明确条件；涉及状态流转时使用条件更新或版本号防止并发覆盖。
- 订单、支付、库存等关键操作必须设计幂等键和重复请求处理。
- SQL 中禁止拼接未经校验的用户输入，优先使用参数绑定。

## 7. 接口与数据校验

- 请求参数在 Controller 层进行格式校验，在 Service 层进行业务校验。
- 分页接口必须限制页码和单页数量，禁止让客户端无限制指定 `pageSize`。
- 返回给前端的错误信息应可理解，但不得泄露 SQL、堆栈和内部实现细节。
- 日期时间统一使用明确时区的类型和格式；服务端统一使用项目约定的时区。
- 文件上传必须校验大小、类型、扩展名和文件名，禁止直接使用用户上传文件名作为本地路径。

## 8. 测试与提交

- 新增业务方法至少覆盖正常路径、参数异常和关键失败路径。
- Controller 测试接口契约，Service 测试业务规则，Mapper 测试数据库映射。
- 每次修改后先运行受影响模块的测试和构建，再启动服务验证接口。
- 提交前删除调试代码、临时文件和本地密码；`.env` 等敏感配置不得提交。
- 提交信息清晰描述改动目的，例如 `feat(order): add order detail query`。

## 9. 本项目的输出约定

- 后续给出的 Java 示例默认遵循本文规范。
- 示例代码会优先使用构造器注入、明确命名、DTO/VO 分层和统一异常处理。
- 涉及微服务的示例会明确服务边界，不直接跨服务访问数据库。
- 业务代码中尽量少用 Lambda 表达式和 Stream 链式操作。
- 简单集合转换优先使用普通 `for` 循环，保证调试过程和执行逻辑清晰。
- MyBatis-Plus 查询优先根据场景选择普通 `QueryWrapper`；复杂查询或字段安全性要求较高时再使用 `LambdaQueryWrapper`。
- 不为了追求代码简短而堆叠多层链式调用，优先保证代码可读性和学习理解成本。
- 连续步骤中已经完成的包和依赖导入，后续代码示例不重复列出；只给出新增或修改的实现内容。
- 用户反馈“完成了”“成功了”“可以了”等明确完成信号后，直接进入计划中的下一步。
