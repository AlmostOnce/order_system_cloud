### [-] P0-1 退款被拒后重新申请会少退钱（复核为误报，未改代码）

- **复核结论：** 审查时的前提有误。店主拒绝时走的是 `REJECTED` 分支，**不释放** `refund_reserved_quantity`；只有经理最终拒绝（`CLOSED`）与用户撤回才调用 `releaseRefund`。因此被拒后重申同样被份数额度挡住，不会出现"份数通过、金额不足"。
- **证据：**
  - `OrderItemMapper.releaseRefund` 只在 `OrderRefundServiceImpl` 的 `withdraw` 与 `decide(manager=true)` 两处调用；

  - `docs/ORDER_REFUNDS.md:22` 明确写"拒绝后仍保留申请额度用于申诉，可撤回释放额度；经理最终拒绝也释放额度"。
- **处理：** 保持现状，不改 SQL。若要放宽语义，应同时改份数额度与金额额度，属于产品规则变更，不在本次修复范围。

- **修复记录（已完成）：**

- **跳过后果：** 任何一次取消链路抖动，都会把可支付订单变成死单。

### [x] P0-4 余额扣款并发下的两处缺陷

- **风险：** 重复扣款导致调用方误判失败；余额流水与真实余额长期不一致。
- **位置：** `user-service/src/main/java/com/hbue/ordering/user/service/impl/UserBalanceServiceImpl.java:149-183`
- **现状：**
  1. `deduct` 先普通 `SELECT` 建立 RR 读视图，再插占位流水；唯一键冲突时**在同一事务里用普通 `SELECT` 回查**；
  2. 扣款成功后用普通 `SELECT` 读余额回填流水的 `balance_after`。
- **触发场景：**
  1. payment-service 对同一 `bizRef` 并发重试：后到事务的 INSERT 阻塞到前事务提交后抛 `DuplicateKeyException`，随后的回查仍用旧读视图，看不到对方已提交的流水 → `concurrent == null` → 重新抛出 → 接口 500。**钱已扣一次，调用方却收到失败**。
  2. 两笔不同 `bizRef` 并发扣款：余额 100，A、B 各扣 10，A 的快照看不到 B 的提交，流水记 `balance_after = 90`，实际是 80。
- **修复记录（已完成）：**
  - 唯一键冲突后的回查改为 `BalanceRecordMapper.selectPayForUpdate`（`FOR UPDATE` 当前读），能看到对端已提交的流水；
  - 扣后余额改为复用已有的 `UserMapper.selectBalanceForUpdate`（`FOR UPDATE` 当前读）。
  - 说明：同一 `bizRef` 已先经结算守卫行锁串行化，问题 1 在正常链路中较难触发；改为当前读属稳健性加固，不改变正常路径行为。
- **测试：** `mvn -pl user-service -am -Dtest=UserBalanceServiceImplTest test` —— 11 个用例全部通过。
- **跳过后果：** 对账错账，退款金额依据流水计算时会继续算错。

## 三、P1 应修（并发放大 / 缓存不一致 / 功能错误 / 无测试）

### [x] P1-10 退款申请持订单行锁跨 Feign 调用

- **位置：** `order-service/src/main/java/com/hbue/ordering/order/service/impl/OrderRefundServiceImpl.java:78-98`
- **问题：** `@Transactional` 内先 `SELECT ... FOR UPDATE` 锁订单行，再远程调 `payments.fact`、`scopes.loadScopes`。payment 慢 10 秒，同订单的接单/核销/退款审批全部阻塞 10 秒；并发下按订单串行叠加，占用连接池。
- **最小修复：** 把只读的 `fact` 调用移到加锁事务之前，锁内只做本地校验与写入。
- **验收：** 给 `fact` 注入延迟，确认锁等待时间不再包含远程耗时。
- **修复记录（已完成）：**
  - `apply` 去掉方法级 `@Transactional`，改为注入 `PlatformTransactionManager` 构造 `TransactionTemplate`（与 `PaymentOrderGateServiceImpl` 同一写法），事务边界只覆盖加锁后的本地读写。
  - 新流程：事务外无锁预读订单确认归属 → 事务外调用 `payments.fact` 校验支付事实 → 显式事务内 `lockRefundOrder` 行锁、二次幂等检查、实付金额一致性校验与写入。锁内不再有任何远程调用。
  - 事务外预读与锁内读取的实付金额必须一致，不一致返回 409 让客户端重试，避免按旧金额校验后按新金额退款。
  - 幂等重放（`byRequest`）在锁前、锁内各查一次：锁前用于跳过远程调用，锁内用于并发相同 `request_key` 时返回先提交结果，避免唯一键冲突暴露成 500。
- **测试：** `mvn -pl order-service -am -Dtest=OrderRefundServiceTest -Dsurefire.failIfNoSpecifiedTests=false test` —— 6 个用例通过；新增 `paymentFactIsCheckedBeforeOrderRowLock` 用 `InOrder` 断言 `fact` 早于 `lockRefundOrder`，改回锁内调用即变红。

### [x] P1-11 四个 Outbox 发布器无租约，多实例重复外发

- **位置：**
  - `order-service/.../ranking/SalesOutboxPublisher.java:39-54`
  - `order-service/.../coupon/CouponConsumeOutboxPublisher.java:73-98`
  - `stock-service/.../messaging/StockEventPublisher.java:31-53`
  - `order-service/.../messaging/OrderTimeoutMessaging.java:64-80`
- **问题：** `pending()` 只做普通 SELECT，发送前不占位、不推进 `next_attempt_at`。部署 2 个实例时同一行会被两个实例在同一秒各发一次；`markPublished` 的条件更新只阻止二次落库，阻止不了二次发送。销量事件重复投递会让统计口径漂移。
- **最小修复：** `pending()` 改为 `FOR UPDATE SKIP LOCKED`，并在发送前置租约（`next_attempt_at = now() + N`）。
- **验收：** 两实例同时跑，同一事件只投递一次（消费端计数器验证）。
- **修复记录（已完成）：**
  - 四个 Mapper 各新增 `lease(eventId, seconds)`：条件更新 `next_attempt_at = now() + seconds`，谓词为"仍未发布且租约已到期"（优惠券为 `status IN ('PENDING','PUBLISHED')`，因为其 PUBLISHED 仍需重投确认）。并发实例的 UPDATE 由 InnoDB 行锁串行化，只有第一个推进成功并返回 1，其余返回 0。
  - 四个发布器在发送前先领取租约，`lease != 1` 直接跳过本行；领取失败不进入失败退避，避免误标对方正在发送的记录。租约 30 秒，大于一次同步发送耗时。
  - `OrderTimeoutOutboxService` 增加 `lease(id, seconds)`，由实现转发 Mapper 条件更新。
  - 未采用 `pending()` 上的 `FOR UPDATE SKIP LOCKED`：`pending()` 在调度方法中处于自动提交，语句结束即释放行锁，跨实例发送期间没有保护作用；真正起互斥作用的是发送前的 CAS 租约。若后续把整轮扫描包进长事务再考虑该写法。
  - 持有租约的实例发送后崩溃，租约到期可被重新领取，保持至少一次投递；消费端仍按事件号幂等（券服务已有，库存/销量事件沿用事件号键）。
- **测试：** `mvn -pl order-service,stock-service -am -Dtest=SalesOutboxPublisherTest,CouponConsumeOutboxPublisherTest,OrderTimeoutMessagingPublishTest,OrderTimeoutMessagingTest,StockEventPublisherTest -Dsurefire.failIfNoSpecifiedTests=false test` —— 5 个用例全部通过；每个发布器各新增一条"两行待发、仅第一行领取成功 → 只发送一次"的用例。未做真实两实例集成验证。

#### [x] a 延迟档位返回越界的第 19 级

- **原判断：** 900 排在 7200 之后，永远不会被选中。
- **复核修正：** 选择逻辑比较的是"数值最大且不超过剩余时间"，与下标顺序无关。剩余时间落在 [900s, 1200s) 时会选中 900 并返回延迟级别 19；而 RocketMQ 默认 `messageDelayLevel` 只有 18 档（1s ~ 2h），级别 19 属于越界值，Broker 会拒收，消息只能靠 outbox 失败重试，超时关单被推迟。
- **修复记录（已完成）：** 删除 900 档，数组严格对齐 RocketMQ 默认 18 档并补充中文注释说明原因。剩余时间超过 2 小时时钳制到最高档 18；消息到期后消费端仍按数据库期限复核并重新投递，因此选择较短档位不会提前关单。
- **测试：** `mvn -pl order-service -am -Dtest=OrderTimeoutMessagingTest -Dsurefire.failIfNoSpecifiedTests=false test` —— 2 个用例通过；新增"任意剩余时间只能返回 0 或 1~18"的扫描用例，重新加入越界档位即变红。**未验证项：** 未连接真实 Broker 验证投递与重投。

#### [x] b PaymentStatus.CLOSED 注释与实际行为不符

#### [x] c Refresh Token 无绝对会话上限、无按用户索引

- **修复记录（已完成）：**
  - 绝对会话期限：令牌 Hash 新增 `issued_at`（会话首次签发时间），轮换时继承；新令牌 TTL 取"单次有效期"与"会话剩余绝对时间"的较小值，持续刷新不再延长登录状态。`AuthServiceImpl` 在刷新前校验，超期直接 401 并删除旧令牌；`refreshExpiresIn` 返回真实剩余秒数，不再误报完整 30 天。旧令牌缺少该字段时按当前时间起算，避免升级瞬间让存量会话全部失效。
