### [-] P0-1 退款被拒后重新申请会少退钱（复核为误报，未改代码）

- **复核结论：** 审查时的前提有误。店主拒绝时走的是 `REJECTED` 分支，**不释放** `refund_reserved_quantity`；只有经理最终拒绝（`CLOSED`）与用户撤回才调用 `releaseRefund`。因此被拒后重申同样被份数额度挡住，不会出现"份数通过、金额不足"。
- **证据：**
  - `OrderItemMapper.releaseRefund` 只在 `OrderRefundServiceImpl` 的 `withdraw` 与 `decide(manager=true)` 两处调用；
  - `committedAmount` 排除 `CLOSED`，与"份数额度仅在 `CLOSED` 释放"完全一致；
  - `docs/ORDER_REFUNDS.md:22` 明确写"拒绝后仍保留申请额度用于申诉，可撤回释放额度；经理最终拒绝也释放额度"。
- **处理：** 保持现状，不改 SQL。若要放宽语义，应同时改份数额度与金额额度，属于产品规则变更，不在本次修复范围。

### [x] P0-2 支付闸门 `closing=1` 永不回退

- **风险：** 一次取消失败即让该订单在支付窗口内**永久无法支付**。
- **位置：**
  - `payment-service/src/main/java/com/hbue/ordering/payment/mapper/OrderPaymentGateMapper.java:9-16`
  - `payment-service/src/main/java/com/hbue/ordering/payment/service/impl/PaymentServiceImpl.java:786-826`
- **现状：** `beginClose` 无条件 `SET closing = 1`，全仓**没有任何复位语句**；`whileOpen` 见到非 0 就抛"订单支付入口已关闭"。
- **触发场景：** 学生取消订单 → 先调 `close`（写在 payment 库，不随订单侧 Seata 全局事务回滚）→ 回补库存时 stock-service 返回 503 → 订单仍为"待支付"（全局回滚），但闸门已关 → 学生再点支付，永久 409，只能等 15 分钟超时自动取消。
- **修复记录（已完成）：**
  - payment-service 新增 `OrderPaymentGateMapper.reopen`、`PaymentOrderGateService.reopen` 及 `POST /internal/payments/orders/{orderId}/reopen`，在行锁内把 `closing` 复位为 0，幂等。
  - order-service 的 `cancelPendingOrder` 在"关单调用异常 / 关单返回非成功 / 关单结果未知 / 关单后回补或释放券失败"四条失败路径上补偿调用 `reopen`；`PAID` 分支不补偿，避免已收款订单被恢复支付入口。
  - 新增用例：`OrderStatusServiceTest` 三条（回补失败补偿、关单异常补偿、已支付不补偿），`PaymentOrderGateServiceImplTest` 两条。
- **测试：** `mvn -pl order-service,payment-service -am -Dtest=OrderStatusServiceTest,PaymentOrderGateServiceImplTest test` —— 21 + 2 全部通过。
- **跳过后果：** 任何一次取消链路抖动，都会把可支付订单变成死单。

### [ ] P0-3 修改角色不失效已签发的令牌

- **风险：** 垂直越权，降权后最长约 30 分钟仍持有原管理权限。

// 示意：与修改密码路径保持一致，让旧令牌在解码时失效

- **跳过后果：** 调岗、封禁、降权都有一段"幽灵权限"窗口。

### [ ] P0-4 余额扣款并发下的两处缺陷

- **风险：** 重复扣款导致调用方误判失败；余额流水与真实余额长期不一致。
- **位置：** `user-service/src/main/java/com/hbue/ordering/user/service/impl/UserBalanceServiceImpl.java:149-183`
- **现状：**
  1. `deduct` 先普通 `SELECT` 建立 RR 读视图，再插占位流水；唯一键冲突时**在同一事务里用普通 `SELECT` 回查**；
  2. 扣款成功后用普通 `SELECT` 读余额回填流水的 `balance_after`。
- **触发场景：**
  1. payment-service 对同一 `bizRef` 并发重试：后到事务的 INSERT 阻塞到前事务提交后抛 `DuplicateKeyException`，随后的回查仍用旧读视图，看不到对方已提交的流水 → `concurrent == null` → 重新抛出 → 接口 500。**钱已扣一次，调用方却收到失败**。
  2. 两笔不同 `bizRef` 并发扣款：余额 100，A、B 各扣 10，A 的快照看不到 B 的提交，流水记 `balance_after = 90`，实际是 80。
- **最小修复：** 两处查询都改为当前读（`SELECT ... FOR UPDATE`），或复用扣款 `UPDATE` 的返回值推算余额；也可参照 `UserWalletServiceImpl.recharge:55` 先锁用户行再判重。
- **验收：** 用真实事务（或 Testcontainers）写并发重试用例；注意现有 `UserBalanceServiceImplTest:109-124` 用 mock 让第二次查询返回记录，属于"假通过"，需要替换。
- **跳过后果：** 对账错账，退款金额依据流水计算时会继续算错。

### [ ] P0-7 聊天广播逐连接回源，并发时跨服务雪崩

- **风险：** 通知链路整体阻塞，连带打满用户服务与订单服务。
- **位置：** `notification-service/src/main/java/com/hbue/ordering/notification/websocket/NotificationSocketHandler.java:194-209`
- **现状：** `notifyChat` 遍历**每一个**在线连接，对每条连接调 `chats.canRead`，其内部包含 `conversations.find` + `users.basic` + `scopes.getScopes` + `orders.context` 共 3~4 次跨服务调用。
- **触发场景：** 1000 个在线连接、每秒 10 条聊天事件（发布器上限每秒 50 条）→ 每秒约 3 万次 RPC、1 万次 SQL，且全部在 Redis 订阅回调线程**串行**执行 → 用户/订单服务被打满，所有通知延迟。
- **最小修复：** 每个事件只查一次会话（拿到 `customerId`、`windowId`），再按 `identity.userId()` 与窗口归属直接筛选连接，不再逐连接回源。
- **验收：** 压测 500+ 连接、10 事件/秒，RPC 次数应与事件数成正比而非与连接数成正比。
- **跳过后果：** 用户量一上来，聊天功能先把整个通知系统拖垮。

## 三、P1 应修（并发放大 / 缓存不一致 / 功能错误 / 无测试）

### [ ] P1-10 退款申请持订单行锁跨 Feign 调用

- **位置：** `order-service/src/main/java/com/hbue/ordering/order/service/impl/OrderRefundServiceImpl.java:78-98`
- **问题：** `@Transactional` 内先 `SELECT ... FOR UPDATE` 锁订单行，再远程调 `payments.fact`、`scopes.loadScopes`。payment 慢 10 秒，同订单的接单/核销/退款审批全部阻塞 10 秒；并发下按订单串行叠加，占用连接池。
- **最小修复：** 把只读的 `fact` 调用移到加锁事务之前，锁内只做本地校验与写入。
- **验收：** 给 `fact` 注入延迟，确认锁等待时间不再包含远程耗时。

### [ ] P1-11 四个 Outbox 发布器无租约，多实例重复外发

- **位置：**
  - `order-service/.../ranking/SalesOutboxPublisher.java:39-54`
  - `order-service/.../coupon/CouponConsumeOutboxPublisher.java:73-98`
  - `stock-service/.../messaging/StockEventPublisher.java:31-53`
  - `order-service/.../messaging/OrderTimeoutMessaging.java:64-80`
- **问题：** `pending()` 只做普通 SELECT，发送前不占位、不推进 `next_attempt_at`。部署 2 个实例时同一行会被两个实例在同一秒各发一次；`markPublished` 的条件更新只阻止二次落库，阻止不了二次发送。销量事件重复投递会让统计口径漂移。
- **最小修复：** `pending()` 改为 `FOR UPDATE SKIP LOCKED`，并在发送前置租约（`next_attempt_at = now() + N`）。
- **验收：** 两实例同时跑，同一事件只投递一次（消费端计数器验证）。

### [ ] P1-12 档口评分批量查询把已删除评价算进去

- **位置：** `comment-service/src/main/java/com/hbue/ordering/comment/mapper/RatingBatchMapper.java:14-25`

- **验收：** 删除评价后批量分与单条分一致。

### [ ] P1-13 商品评分读缓存永不失效

### [ ] P1-16 支付密码失败计数非原子设置 TTL

- **位置：** `user-service/.../PayPasswordServiceImpl.java:319-336`

- **验收：** 连续错误达阈值后锁定，TTL 到期自动解锁。

## 五、建议落地顺序

**批次 1：资金与支付（P0-1、P0-2、P0-4、P1-16）**
先保证钱算得对、付得出去。每修一条补一条能失败的测试，避免回归。

**批次 2：权限与内部接口（P0-3、P0-5）**
降权即时生效、内部密钥 fail-closed。可与批次 1 并行，互不冲突。

**批次 3：可用性与前端阻塞（P0-6、P0-7、P0-8、P0-9）**
测试门禁恢复、聊天广播改造、评价页 500、前端编译阻塞。

**批次 4：一致性与幂等（P0-11、P1-10、P1-12、P1-13、P1-14、P1-15）**
Outbox 租约、退款锁范围、评分与窗口缓存、停用餐厅止血。

**批次 5：测试补全与清理（P1-17、P1-18、P2-19、P2-20 及 9 条小项）**
补齐券/余额测试，清理死代码与死配置。

> 依赖提示：批次 1 的余额改动会触及 `user-service` 资金核心，建议单独一个提交、单独回归；批次 4 的缓存失效与批次 3 的接口改造可能同时动 `product-service`/`comment-service`，注意提交拆分。
