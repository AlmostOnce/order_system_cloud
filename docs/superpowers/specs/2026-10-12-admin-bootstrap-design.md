# 权限角色与首个管理员账号引导设计

## 背景与目标

当前认证和用户服务已经支持用户注册、BCrypt 密码存储及角色写入 JWT。公开注册由 `user-service` 固定赋予 `CUSTOMER`，请求对象不接受角色字段，因此客户端不能通过注册参数把自己提升为管理员。项目需要沿用原点餐系统的业务角色，同时补齐安全创建首个 `SYSTEM_ADMIN` 账号的初始化流程。

本设计为本地开发和后续部署提供一个显式开启、一次性使用的管理员引导流程，不新增公开的管理员创建 HTTP 接口，也不改变现有用户注册流程。

## 目标角色

| 角色编码 | 业务身份 | 业务数据范围 |
|---|---|---|
| `CUSTOMER` | 顾客 | 仅能查看和操作本人订单、支付等数据 |
| `STALL_MANAGER` | 档口负责人/店主 | 仅管理分配给自己的档口、菜单及相关订单 |
| `RESTAURANT_MANAGER` | 餐厅经理 | 管理所属餐厅下的档口和经营数据 |
| `GENERAL_MANAGER` | 总经理 | 跨餐厅经营管理及汇总数据 |
| `SYSTEM_ADMIN` | 系统管理员 | 平台级账号、角色和系统配置管理 |

角色表示“能执行哪类操作”，`window_id`、`restaurant_id` 等授权范围表示“能操作哪些数据”。管理接口必须同时校验角色与数据范围，不能只凭 JWT 中出现某个角色就允许访问任意档口或餐厅数据。

## 现状与边界

- `user-service` 是 `users` 表和 `role_code` 的唯一数据所有者；管理员账号应由该服务创建。
- 当前数据库仅有 `users.role_code VARCHAR(20)` 字段，没有角色字典表或权限表；本机当前存量用户均为 `CUSTOMER`。字段可保存上述角色编码，但每个用户当前只能保存一个角色。
- 本次目标角色按原系统业务范围统一为上表五种；其中本次实现范围先聚焦首个 `SYSTEM_ADMIN` 引导，其他角色的创建、分配和数据范围授权按对应业务接口逐步落地。
- 初始管理员使用 `SYSTEM_ADMIN`，不再使用含义较宽泛的 `ADMIN`。
- `auth-service` 登录后会将用户角色写入 JWT 的 `roles` 声明；管理员登录后可获得 `SYSTEM_ADMIN` 角色声明。
- `user-service` 当前只配置了 BCrypt 密码编码，没有 JWT 资源服务和管理员接口。因此本次只建立管理员身份，不新增无实际业务用途的“权限测试接口”。具体管理接口形成时，再在业务服务内实施角色校验。

若未来一个用户需要同时担任多个角色，或在不同档口/餐厅拥有不同授权范围，应将单一 `role_code` 演进为用户角色关联及范围授权模型；本次不提前增加该数据库模型。

## 方案

在 `user-service` 增加启动期管理员引导组件，由现有用户业务层完成查询、校验和写库。只有显式开启 `USER_ADMIN_BOOTSTRAP_ENABLED=true` 时才运行；账号、手机号和初始密码分别从 `USER_ADMIN_BOOTSTRAP_USERNAME`、`USER_ADMIN_BOOTSTRAP_PHONE`、`USER_ADMIN_BOOTSTRAP_PASSWORD` 读取。所有字段均无内置账号或密码默认值。

引导逻辑遵循以下规则：

1. 未开启时完全不执行，不要求提供管理员配置。
2. 开启但账号、手机号或密码缺失，或字段格式不合法时，服务启动失败并给出不含敏感值的配置提示。用户名沿用用户表上限（2–50 个字符），手机号沿用现有 11 位中国大陆手机号格式；管理员初始密码长度为 12–64 个字符。
3. 已存在启用且未删除的 `SYSTEM_ADMIN` 时跳过创建，不更新其密码，也不输出密码或密码哈希。
4. 尚无管理员时，使用 `USER_ADMIN_BOOTSTRAP_*` 配置创建用户，角色固定为 `SYSTEM_ADMIN`，密码经 BCrypt 编码后保存。
5. 如果配置的用户名或手机号已被非管理员账号占用，拒绝自动提权并使初始化失败；不改变已有用户的角色或密码。
6. 初始化只允许在一个 `user-service` 实例上临时开启。创建后应关闭开关并移除初始密码环境变量；正常运行的多实例不得持续启用引导。

不创建密码默认值，不接受 HTTP 请求中的角色，不提供可由外部调用的 bootstrap endpoint，不改动其他角色或已有账号。

## 启动配置

`user-service` 的 `application.yml` 将绑定上述四个环境变量。默认状态为关闭，账号字段默认空值；真实初始密码通过 IDEA 运行配置的环境变量输入，不写入 Git 跟踪的 YAML、`.env.example` 或日志。示例配置仅描述变量名称，不包含可用密码。

## 数据流

```text
IDEA / 部署环境变量
        ↓ 显式开启
user-service 启动引导组件
        ↓ 调用用户业务服务
检查已有 SYSTEM_ADMIN 与账号唯一性
        ↓ 无管理员且账号未占用
BCrypt 编码密码并写入 users（role_code=SYSTEM_ADMIN）
        ↓
AuthService 后续登录签发包含 SYSTEM_ADMIN 的 JWT
```

## 错误处理与安全

- 配置不完整、初始账号冲突、数据库写入失败时，启动流程失败，不降级为普通用户注册，也不静默创建默认管理员。
- 日志只说明初始化、跳过或失败原因，不记录初始密码、BCrypt 哈希或完整凭据。
- 已有管理员时只跳过；修改管理员密码仍走正常的受控密码管理流程，不由启动配置覆盖。
- 用户服务与 Gateway 对 JWT 的角色校验不在本次交付范围内；管理员身份本身不自动产生服务端权限，后续必须由具体管理 API 在业务服务内校验 `SYSTEM_ADMIN`。

## 验收与测试

- 引导开关关闭时，不创建账号。
- 开启且管理员不存在时，创建唯一 `SYSTEM_ADMIN`，密码以 BCrypt 哈希保存，不能以明文匹配。
- 已存在启用管理员时再次运行不新增账号、不覆盖密码。
- 配置用户名或手机号被普通用户占用时，初始化失败且该用户仍保持原角色。
- 开关开启但必填项缺失、用户名/手机号格式不合法或密码不在 12–64 个字符范围内时，初始化失败且日志不包含凭据。
- 现有公开注册回归测试确认新账号仍固定为 `CUSTOMER`，不受 bootstrap 配置影响。

## 后续独立工作

在出现真实的管理接口时，再为相应业务服务接入 JWT 资源服务校验，映射 JWT `roles` 声明，并按 `STALL_MANAGER`、`RESTAURANT_MANAGER`、`GENERAL_MANAGER` 或 `SYSTEM_ADMIN` 实施角色与数据范围检查；Gateway 的认证不能替代业务服务的授权。
