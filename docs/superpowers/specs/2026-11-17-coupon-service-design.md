# 优惠券服务方案

> 状态：方案建议稿，业务规则确认后再进入实现计划。
> 范围：后端优惠券服务结构、订单/支付/退款衔接、学生端与管理端职责及分阶段实施安排。

## 1. 背景与目标

项目已有独立的商品、购物车、订单、支付、库存、用户和统计服务。优惠券涉及券的发行与领取、订单优惠金额、支付金额、退款金额和促销成本归属，建议作为独立业务服务建设，避免将券生命周期与订单编排混在一起。

目标是先支持简单、可核算的满减券，并确保重复请求、并发抢券、取消、支付和退款下的金额与券状态一致。首期只做满减券；积分、会员等级、折扣券、赠券营销、券叠加及自动择优暂不纳入。

## 2. 主流平台做法与对本项目的启示

- 美团外卖规则将商家代金券定义为商家自行发行、仅在该商家店铺使用的优惠券；平台的补贴活动则要求说明补贴对象、方式、条件和时间。商家自建促销与平台补贴因此是不同经营方式。[美团外卖代金券使用规则](https://i.waimai.meituan.com/c/rules/%E7%BE%8E%E5%9B%A2%E5%A4%96%E5%8D%96%E4%BB%A3%E9%87%91%E5%88%B8%E4%BD%BF%E7%94%A8%E8%A7%84%E5%88%99.html)、[美团平台价格行为规范](https://rules-center.meituan.com/m/detail/guize/406004?activeRule=1)
- 京东面向用户的规则区分全品类券、限品类券和店铺券，并按券的适用范围说明门槛及同一订单的使用关系。[京东优惠券说明](https://help.jd.com/user/issue/169-1077.html)
- 淘宝平台品类券需要商家报名并由平台审核，协议又将平台出资金额作为活动项单独说明。这表明券的经营发起方、适用商家和优惠资金承担方需要分别定义；平台活动的资金口径以活动规则为准。[淘宝平台品类券活动合作协议](https://terms.alicdn.com/legal-agreement/terms/b_end_product_protocol/20250508185535922/20250508185535922.html)

**结论：**成熟平台通常同时提供平台范围券与店铺/商家券，券的适用范围可以独立于发起主体；平台促销也可能要求商家报名。对本项目而言，“谁创建/发行”与“谁承担优惠金额”必须分别记录，不能只靠一个券类型推导资金归属。平台活动和商家活动的优惠叠加规则也需要明确展示；首期采取一单一券、不叠加，减少金额和退款复杂度。

## 3. 推荐方案

### 3.1 发行与出资

长期支持两种发行主体：

1. **平台/食堂管理侧发行的平台券**：可面向全校，也可限定一个或多个窗口；资金承担方在活动创建时明确指定。
2. **窗口经营方发行的店铺券**：仅适用于其有权限经营的窗口；优惠成本记到该窗口。

共同营销活动可以以后增加平台与窗口分摊，但必须在活动规则、订单优惠快照和经营核算中逐笔记录两方金额，首期不做分摊。

**实施顺序建议：**首期只开放经授权的管理角色创建、由平台/食堂活动预算承担的券，并允许限定窗口。项目当前源码说明了学生余额支付和订单支付流程，但没有单独的商家结算服务；在窗口优惠成本的结算、对账和经营报表具备承接能力前，不开放窗口自助发行或窗口出资券。第二阶段再开放窗口券，并要求窗口授权、出资流水和退款冲正核算一并上线。

这与主流平台最终支持平台券、店铺券两种来源的做法一致，同时避免第一阶段先发出窗口承担、却没有可核对成本的优惠。平台活动同样需要预算上限和支出统计，不能将其当作无成本优惠。

### 3.2 首期业务规则

- 只支持固定金额满减券，例如“满 30 元减 5 元”。
- 一笔订单最多使用一张优惠券，不与其他优惠叠加。
- 适用范围为全校或指定窗口；不支持商品级适用范围。
- 先支持学生主动领取；同一用户同一券模板最多领取一次。
- 领取量、每人限领数、可领取时间、使用有效期均由模板明确设置。
- 优惠金额不得超过适用商品金额；建议保留最低实付金额，避免同步引入零元支付流程。
- 券展示清楚门槛、范围、有效期及适用限制；优惠活动不得隐藏关键条件。
- 已发出的券引用不可被后台静默改写。停止领取、停止使用新券和作废已领取券应是不同的管理动作，并有操作记录。

### 3.3 不在首期范围

折扣券、菜品券、兑换码、自动派券、券包、转赠、多券叠加、平台与窗口联合出资、面向店铺的结算后台及促销效果归因。需要这些能力时单独评估，不提前铺设泛化规则引擎。

## 4. 服务与仓库结构

新增两个后端模块，遵循当前 Maven 多模块仓库的模块与分层方式；此处仅是方案，未创建模块。

```text
coupon-api/
└── src/main/java/com/hbue/ordering/coupon/api/
    ├── client/       服务间 Feign 契约
    ├── dto/          请求与响应契约
    └── vo/           需要被其他服务读取的视图

coupon-service/
└── src/main/java/com/hbue/ordering/coupon/
    ├── controller/   学生、管理和内部接口
    ├── service/      券模板、领取、校验、锁定、核销和释放
    ├── mapper/       条件更新、唯一约束和分页查询
    ├── model/        持久化对象
    ├── dto/vo/       服务自身接口模型
    ├── client/       订单等服务的契约客户端（确有需要时）
    ├── messaging/    可靠处理订单支付事件
    ├── task/         锁券异常对账与恢复
    └── config/       服务与安全配置
```

服务分工：

| 模块 | 职责 |
| --- | --- |
| `coupon-service` | 拥有券模板、用户持券和优惠资金归属记录；校验领取资格、适用范围和状态迁移。使用独立 `coupon_db`。 |
| `coupon-api` | 提供订单服务所需的接口契约，不承载业务实现，也不允许其他服务直接查询 `coupon_db`。 |
| `order-service` | 核验商品价格，编排优惠试算与锁券，确定优惠分摊，保存订单金额快照，并按实际支付快照处理退款。 |
| `payment-service` | 按订单服务确认的应付金额扣款和退款；不重新计算券规则。 |
| `gateway-service` | 路由和外部访问认证；学生接口仅允许 CUSTOMER，管理接口按授权管理角色及数据范围控制。 |
| 学生端 uni-app | 仅提供学生领券、我的券、结算选券及订单金额展示。 |
| Vue 管理端 | 提供授权管理角色创建/停发券、查看领取与核销统计；管理端仓库接入位置需后续查证。 |

### 4.1 数据表建议

首期采用三张核心表，结构只覆盖满减券：

| 表 | 关键字段/约束 |
| --- | --- |
| `coupon_template` | 模板编号、发行方类型与 ID、出资方、适用窗口范围、门槛金额、优惠金额、发行上限、每人领取上限、领取时间、有效期、状态、创建人。已发行模板的核心优惠规则不可原地修改。 |
| `user_coupon` | 用户 ID、模板 ID、领取时间、有效期快照、状态、锁定订单 ID、核销时间；用户与模板组合唯一约束，条件更新保证库存和状态不会并发超发/重复使用。 |
| `coupon_use_record` | 用户券 ID、订单 ID、操作类型、订单优惠金额快照、平台/窗口承担金额、幂等业务键、结果及时间；同一用户券的一次订单使用需有唯一约束。 |

平台承担时窗口金额为零；首期不允许联合出资。后续窗口券上线前，需要明确营销费用如何进入窗口应收/经营报表，以及退款后的冲正口径。

## 5. 核心流程与一致性

### 5.1 试算

1. 学生端请求可用优惠券及结算试算，只提交用户券 ID，不提交优惠金额。
2. 订单服务调用商品服务取得当前真实商品价格。
3. 优惠券服务校验券归属、有效期、窗口范围、最低消费和当前状态，并返回规则与优惠试算。
4. 试算只用于展示，不锁定券；正式下单时重新核价和验证。

优惠券服务不得信任客户端金额。优惠资格的校验结果要基于订单服务核实后的窗口和商品金额。

### 5.2 下单与锁券

1. 订单服务纳入用户券 ID 及订单商品到下单幂等请求摘要，避免相同幂等键被用于另一张券。
2. 正式下单时重新核价、验证券并锁券；锁定动作以数据库条件更新和唯一约束作为并发防线。
3. 订单服务保存原价、优惠金额、应付金额、券规则快照和优惠分摊。订单与券锁定、库存扣减须复用项目现有分布式事务边界；任何步骤失败时不得留下无主锁券或已扣库存的半张订单。
4. 支付服务仅按订单应付金额创建支付单。券服务超时/不可用时，选择优惠券的下单请求失败并提示重试；不允许静默按原价完成用户选券订单。无券订单照常进行。

### 5.3 支付、取消与过期

- 确认支付成功后，将券从已锁定转为已核销；事件消费按订单和用户券幂等，使用订单侧 Outbox 或等效可靠消息机制推进。
- 用户主动取消或订单超时关闭后释放锁定券；如果此时券已过有效期，状态转为过期而不是重新可用。
- 释放或核销必须检查关联订单状态。不能仅因锁定时间过期就释放，因为订单可能已成功扣款但事件尚未到达。
- 定时对账只修复确认无支付且订单已关闭的异常锁券，并记录修复结果，不能覆盖已核销状态。

### 5.4 金额快照与退款

当前 `orders.total_amount` 是商品金额合计，支付服务读取该金额扣款；订单明细 `line_amount` 用于退款金额计算。优惠接入不能只在支付前临时减价。

建议保留 `total_amount` 表示原商品合计，新增订单级 `discount_amount` 和 `payable_amount`；明细保存分摊的 `discount_amount` 与优惠后金额。支付服务改为读取 `payable_amount`，支付成功对账和退款验证也以应付/实付金额为准。历史订单优惠额为零，应付额等于原总额。

满减优惠按适用商品金额比例分摊到明细，以分为单位处理舍入并将尾差固定归属一条明细。部分退款只能按该明细的优惠后实付份额计算，累计退款不可超过实际支付金额。支付后全额退款是否退回优惠券需业务定案；建议首期不退券，防止已兑现优惠再次使用。未支付取消则释放券，过期券不恢复可用。

## 6. 接口建议

精确路径和 DTO 在设计确认后参照当前 API 命名规范确定，首期只需以下接口能力：

| 调用方 | 能力 |
| --- | --- |
| 学生端 → 优惠券服务 | 查询可领取模板、领取、查询本人券；用户身份由服务端 Token 提取。 |
| 订单服务 → 优惠券服务 | 试算、锁定、核销、释放；内部接口校验调用身份，并以订单号/幂等键防止重复操作。 |
| 管理端 → 优惠券服务 | 创建模板、开始/停止领取、停用未使用券、按权限分页查询发放与使用记录。 |

所有列表使用有界分页；用户只能访问自己的券；窗口管理角色只能管理授权窗口；总经理/系统管理范围使用现有数据范围服务约束。前端隐藏入口不能代替后端鉴权。

## 7. 分阶段实施计划

| 阶段 | 交付内容 | 主要验收点 |
| --- | --- | --- |
| 0. 规则定稿 | 明确发行角色、平台预算主体、适用窗口、领取与有效期、零元单策略、支付后退券规则和费用报表口径；核实 Vue 管理端仓库。 | 各种下单/取消/支付/退款路径有明确规则，窗口券是否以及何时由窗口出资已决定。 |
| 1. 服务基础与平台券 | 新增 `coupon-api`、`coupon-service`、独立数据库迁移、注册/配置和网关路由；管理侧创建活动，学生领券及查看持券。 | 权限、每人限领、发行上限和模板变更限制正确；平台承担优惠支出可按订单核对。 |
| 2. 订单与支付金额 | 结算试算、正式锁券、订单金额字段、优惠快照与分摊；支付按应付金额扣款，保证下单幂等。 | 同券并发竞争只能绑定一个有效订单；金额恒等于原价减优惠；创建失败不残留券锁。 |
| 3. 取消、核销与售后 | 支付成功核销、取消/超时释放、乱序与重试保护、部分退款按优惠后金额计算、异常对账。 | 重复消息、支付与取消竞争及锁券超时均不重复用券或超额退款。 |
| 4. 学生端与管理端验收 | 学生端领券、结算选券和订单优惠展示；在确认过位置的 Vue 管理端接入活动管理。 | 从创建/领取到支付/取消/退款的完整链路通过业务验收，所有角色和窗口数据范围正确。 |
| 5. 窗口券（后续） | 先补齐窗口优惠成本报表、退款冲正和管理端数据范围，再开放窗口角色创建/出资。 | 单笔优惠支出、退款冲正、窗口维度汇总能相互对账后才开放。 |

每阶段适用的源码检查和测试应在实现时安排；后端 Maven 命令仍须遵守项目约束，除非用户在该次请求明确授权，否则不运行 Maven。数据库迁移按项目既有约定，在脚本检查完成后核对开发库和重复执行风险，再执行并记录结果。

## 8. 需要业务确认的事项

1. 首期优惠预算是否明确由平台/食堂管理侧承担，是否允许限定窗口？本方案建议“是”。
2. 首期是否保留最低实付金额，避免零元支付？本方案建议“是”。
3. 支付后全额退款时是否退券？本方案建议首期不退券。
4. 首期发券、查数据由哪些现有管理角色负责？需按代码中现有角色和数据权限映射，不新增未经确认的角色。
5. 管理端 Vue 仓库实际位置及当前结算/窗口成本核算流程是什么？需查证后才能排定窗口出资券阶段。

## 9. 项目现状依据

- `README.md` 的服务模块表列出当前可部署业务服务，没有单列商家结算服务；支付服务描述为支付编排与记录，用户余额由用户服务管理。
- `order-service` 当前创建订单时从商品服务核价并保存订单与明细金额快照，订单创建、取消和超时已有分布式事务流程。
- `payment-service` 当前创建支付单时读取订单 `totalAmount`；余额支付将实际金额交由用户服务扣款。
- `order-service` 退款流程依照明细金额及份数核算，并校验真实支付金额。因此优惠必须成为订单持久化快照，并覆盖部分退款分摊规则。
- 学生端/管理端边界遵循项目 `AGENTS.md`：uni-app 仅承载 CUSTOMER，非学生管理功能接入专门 Vue 管理端；管理端源码位置仍待核实。
