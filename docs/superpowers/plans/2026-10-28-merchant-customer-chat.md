# 商家与顾客订单沟通实施计划

**目标：** 支付成功后，顾客和该订单所属窗口的授权商家可以围绕订单发送消息，并在离线或断线后查看历史。

**架构：** 第一阶段将聊天作为 `notification-service` 内独立业务模块，复用其身份认证与 WebSocket 连接，但会话、消息、未读与订单通知分别建模。订单服务负责证明订单归属及支付状态，现有数据范围服务负责确认商家是否有当前窗口权限；MySQL 保存事实数据，WebSocket 负责在线实时推送，Redis 用于多实例在线事件转发，RocketMQ 仅用于跨服务通知等需要可靠重试的异步事件。

**技术：** Spring Boot 3.5、现有 JWT 与 Redis 黑名单、MySQL/Druid、WebSocket、Redis、uni-app x；网关和商家端对接以现有实际项目为准。

**前置方案：** [通知服务实施方案](../../NOTIFICATION_SERVICE.md)。当前通知服务尚未完成，不能假定其接口、消息或连接机制已经可用。

## 全局约束

- 用户要求未经当前请求明确授权，不运行或触碰 Maven；执行本计划时注册新服务和依赖需要另行取得相应明确授权。
- 业务事实由服务端校验；客户端提供的用户、商家或窗口 ID 不作为身份与授权依据。公开 API 不返回用户内部 ID。
- 不读取、修改或清空现有订单、聊天以外的 Redis 数据；不把聊天正文、访问令牌或连接票据写入日志。
- 本文是下一步计划，不代表代码、迁移、MQ、WebSocket 或用户界面已实现。

## 首期产品规则

- 一笔订单对应一个会话。顾客只可进入自己的订单；商家需对该订单窗口有当前有效的管理权限。一个窗口有多个授权商家时，授权商家共同处理同一会话；发送时记录实际操作人，不能把平台或食堂范围的管理权限直接等同于店主身份。
- 已支付、制作中、待取货允许建立和使用会话。待支付、已取消不能建立。已完成后的消息可见性与是否继续发送尚待用户确定；在确认前不开发任何自动关闭时间或清理规则。
- 首期仅支持文本；图片、语音、撤回、客服转接、消息删除及敏感内容审核另行规划。明确消息长度与频率限制时以最终产品要求为准。
- 顾客从订单详情进入“联系商家”；商家从所属窗口的订单列表/详情进入“联系顾客”。还需确认商家端项目及入口位置，不能假定顾客端已有商家操作页面。
- 对方离线时消息先入库，在线时即时提示；未读是按参与方记录的阅读进度，不等于服务端推送成功。用户主动打开会话并确认阅读后才更新进度。

## 领域与数据

1. `chat_conversations`：公开 UUID、订单编号、窗口编号、顾客内部 ID、创建时间、最后消息时间；订单编号唯一。并发首次进入时依靠唯一约束防止建立两个会话。
2. `chat_messages`：公开 UUID、会话内部引用、会话内递增顺序、发送者内部 ID、身份快照、文本、客户端幂等键、创建时间。相同发送者、会话及幂等键唯一；同键不同内容返回冲突。
3. `chat_read_state`：会话、参与用户及最后已读消息序号。权限变更后不把旧商家永久视为当前授权人；每次读取、发送、订阅以及重连都重新验证当前权限。
4. 分页和补消息按会话内序号实现；外部接口使用公开会话/消息标识和安全游标，不泄露内部数据库主键。数据保留、历史权限与清理期限在实施前确认。

## 通信和一致性

1. 客户端通过 HTTPS 携带现有 Bearer 登录凭据申请**短时、一次性、限制用途的 WebSocket 连接票据**。浏览器 WebSocket 无法自定义 Authorization，握手时可携带此票据，但必须配置网关和应用不记录票据，票据不能是长期访问令牌；服务端原子消费票据并再次校验当前会话、黑名单与过期时间。uni-app x 各端支持差异需实测。连接建立后设置最大连接时长并定期重新校验认证与权限，注销或权限撤销后关闭连接。
2. 客户端发送消息时携带会话 UUID 和客户端生成的幂等键；服务端校验身份、订单支付状态、当前窗口范围和内容，持久化成功后返回服务端消息 ID 与顺序号。失败不显示为已送达；超时重试复用同一幂等键。
3. 提交后的在线事件在本实例推送；多实例通过 Redis Pub/Sub 广播到有该用户连接的实例。Pub/Sub 只承担实时提示，不保证送达；断线、Redis 中断或推送丢失时通过消息历史与游标补齐，避免承诺“实时事件必达”。为减少提交后进程崩溃造成的在线提示遗漏，可在同事务内写聊天事件 outbox，由后台转发；消息列表仍是事实来源。
4. WebSocket 自动重连采用有限的指数退避，页面重新认证后按最后已收到的服务端序号补拉；对重复消息按服务端 UUID 去重。会话消息用持久序号排序，不用客户端时间判断先后。
5. MQ 用于跨服务事件时，通过各自事务 outbox、事件唯一键与消费幂等保障最终一致；聊天消息不需要因为使用了 WebSocket 就再无条件通过 RocketMQ 转发。离线接收人可由通知服务生成“有新消息”聚合提醒，避免每条消息造成通知轰炸，具体策略待产品确认。

## 接口草案

路径只作为实施草案，遵循网关现有 `/api` 路由与统一响应格式，最终以实际接口定义为准。

| 操作 | 草案接口 | 约束 |
| --- | --- | --- |
| 获取或创建订单会话 | `POST /chat/conversations`，传订单标识 | 服务端检查本人订单或商家当前窗口权限及订单状态；并发幂等 |
| 会话列表 | `GET /chat/conversations` | 仅当前用户可访问的会话，按最新消息排序 |
| 读取历史和断线补齐 | `GET /chat/conversations/{id}/messages` | 游标分页；读取前再次鉴权 |
| 申请连接票据 | `POST /chat/ws-ticket` | 用户认证、短期一次性、限制用途及有效期 |
| 建立连接 | `GET /chat/ws` | 通过网关升级连接并验证短时票据；不记录票据 |
| 发送 | WebSocket `message.send` | 认证会话、幂等键、服务端确认及可重试错误 |
| 标记已读 | `POST /chat/conversations/{id}/read` | 最后已读位置不能倒退，且不能超过本会话可见消息 |

## 实施阶段和验收

- [ ] **阶段一：权限与持久化。** 确认商家窗口权限的现有内部 API、历史订单语义和支付状态来源；补充订单核验契约、建表迁移、会话唯一性与文本消息持久化。验证本人/他人订单、未支付/已取消、多个商家以及权限撤销；并发创建只产生一个会话。
- [ ] **阶段二：消息与历史。** 实现幂等发送、分页、补拉及阅读进度。验证重复提交、同键不同内容、并发消息顺序、分页无重复遗漏、跨用户越权和未读位置不能倒退。
- [ ] **阶段三：实时连接。** 接入短期一次性票据、网关 WS 路由、多连接管理与 Redis 多实例提示。验证票据过期/重放、令牌注销、连接断开、重连补拉、实例重启和 Redis 暂不可用；分别验证浏览器与目标 uni-app x 平台。
- [ ] **阶段四：用户端与商家端。** 完成订单详情入口、会话列表、聊天页、发送中/失败重试、未读和空态；商家端仓库与实际路由确认后接入。验证小屏、键盘遮挡、长文本、弱网、登录切换及通知入口一致性。
- [ ] **阶段五：可靠性与上线准备。** 按最终设计补充 outbox、监控与必要的消息队列重试；验证数据库提交后进程崩溃、重复投递、慢消费者、消息压积和权限撤销。记录部署顺序、回滚方案和保留策略。
