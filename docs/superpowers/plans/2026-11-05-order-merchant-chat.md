# 支付后联系商家：业务与实施方案

> 状态（2026-11-06）：后端与学生端源码已实现，正在静态检查及前端逻辑验证；未执行数据库迁移、启用开关、发布网关配置或运行后端构建。商家管理端按用户要求暂不实现。

**目标：** 顾客支付订单后，从订单详情进入与该窗口商家的实时文字会话；离线消息可查询，断线可恢复。

**架构：** 在现有 notification-service 内增加独立聊天业务，复用认证、一次性票据、WebSocket和Redis跨实例转发基础；会话、消息与阅读进度独立于订单通知。MySQL是消息事实来源，消息提交后才确认成功与触发推送。

**技术：** 现有Spring Boot、MyBatis-Plus、MySQL/Druid、common-redis、WebSocket、uni-app x及专用Vue管理端。不新增聊天服务、STOMP框架或中间件。

## 一、已经查证的基础与缺口

- 通知服务已有 NotificationTicketService、NotificationHandshakeInterceptor、NotificationSocketHandler、NotificationSocketBus，以及30秒一次性连接票据；不是从零建立长连接。
- 当前 /notifications/ws 仅输出 notification.changed；Handler没有实现聊天收包，用户端 store/notifications.uts 也尚无聊天事件分发。复用连接不等于已有聊天能力。
- 现有Redis广播只传用户编号，不能直接承担聊天消息路由；需扩展类型化事件，保留旧通知协议兼容。
- OrderInternalController已有受内部令牌保护的订单查询；OrderInternalVO含归属和状态，但缺少窗口编号。优先扩展现有订单API契约或新增最小聊天上下文接口，不假定已有完整聊天授权接口。
- UserScopeInternalClient、DataScopeService已有范围查询。通用范围支持平台/餐厅管理，不能直接把“能管理这个窗口”解释成“能读取顾客聊天”。聊天只放行明确获窗口经营授权的店主角色。
- 通知安全配置当前只放行 /notifications/**；若新增 /chat/**，必须同步网关路由和通知服务安全规则。仅更新页面不能接通。
- 当前E盘根目录只查到后端和学生端仓库，未定位专用Vue管理端。实施前需确认其实际位置，不在uni-app中新增商家聊天操作。

## 二、业务规则

### 已由本次需求明确

1. 支付后才出现“联系商家”。服务端仍需校验，不能只依赖按钮可见性。
2. 围绕订单与对应商家实时WebSocket交流。
3. 学生功能放uni-app，商家功能放专用Vue管理端。
4. 用户已补充明确：系统订单通知与商家会话全部放在现有通知中心，不另建聊天中心或Tab。订单详情按钮只是直达对应会话的快捷入口。
5. 点击“联系商家”就是创建会话的触发动作：服务端校验支付状态和归属后创建并返回会话；已经存在则返回原会话。支付成功不自动创建，发送第一条消息也不是创建前提。

### 首期采用规则（2026-11-06用户已确认）

| 项目 | 建议规则 |
| --- | --- |
| 会话粒度 | 一笔订单一个会话，多次进入复用；一个店铺有多笔订单时分会话，展示订单号与菜品摘要 |
| 可发消息状态 | 已支付、制作中、待取货；待支付与已取消不能创建会话 |
| 订单已完成 | 完成后24小时内可继续发消息，之后只读 |
| 消息类型 | 首期纯文字，1至500个字符；图片、语音、撤回不在首期 |
| 商家参与者 | 当前绑定该窗口的店主共同处理，保存实际发送人；店主被撤权后不能继续收取、查询或发送 |
| 历史保留 | 首期不自动删除历史；正式部署前再确定保留与清理规则 |
| 未读语义 | 顾客个人已读；商家按实际操作人分别已读，不让一位店主阅读替其他人全部清零 |
| 频率限制 | 每个用户每秒最多2次、每分钟最多30次发送；按账号跨连接限制，重试先做幂等判断 |

订单页短暂显示支付成功而订单尚未推进时，展示“正在同步订单状态”，确认服务端订单为已支付后才开放聊天；不接受客户端传“我已支付”作为证明。状态或授权服务不可用时暂停写入，Toast提示重试，不默认放行。

## 三、学生端与商家端体验

### 学生端

1. 已支付订单详情增加“联系商家”。点击后调用创建或获取会话接口，成功才跳转聊天页；按钮等待期间禁止重复点击，失败用Toast提示并停留原页。创建成功即出现在通知中心，即使尚未发送消息；空会话显示“暂无消息”，未读数为0。重复点击、不同设备同时点击均复用订单唯一会话，不因网络超时而另建会话。支付成功本身不创建会话。
2. 现有通知中心（底部“消息”页）是统一入口，保留“订单中心”系统会话，与商家会话共同呈现在同一个会话列表。商家行显示店铺头像、名称、订单摘要、最新消息、时间与未读数。不新增独立聊天中心、额外Tab或必须切换的列表分类；仅各会话点入后的记录分开，避免把商家文字写入订单中心的系统通知记录。订单详情快捷入口打开的就是此处同一个会话。
3. 聊天页顶部显示店铺名，下方可折叠订单摘要并跳转订单详情。消息按服务端顺序排列，向上滑到顶部加载旧消息。
4. 底部固定文字输入与发送按钮，键盘升起后输入框保持可见。本人气泡在右、商家在左，展示头像和必要时间分组，不标注未经确认的“已送达”。
5. 发送中显示等待标识，服务端入库确认后变为成功；超时显示失败/待确认和重试入口，复用同一个客户端消息UUID，不能产生重复消息。
6. 进入前台、重连、发现消息序号缺口时补拉；阅读进度只在会话可见且消息已渲染阅读后提交。历史补拉不把列表自动跳回底部。
7. 校验、弱网和失败用Toast；关闭确认等场景复用统一confirm-dialog。会话过期保持清晰只读状态，不再显示可发送输入框。

### 专用Vue管理端

窗口订单详情“联系顾客”和消息会话列表两个入口。展示顾客头像/昵称和订单摘要，按授权窗口查询；多个店主共用会话但显示实际发送人。管理员、餐厅经理不因拥有广泛管理范围而自动获得私人聊天权限。管理端仓库未确认前，只完成后端契约和学生端，不宣称双端联调完成。

## 四、持久化设计

沿用 notification_db，新增以下表，使用DO → Mapper → Service接口 → ServiceImpl → Controller，DTO/VO与存储模型分离；MyBatis-Plus访问MySQL，不新增Repository/JPA层。建表、字段和索引均写中文注释。

| 表 | 主要字段与约束 |
| --- | --- |
| chat_conversations | 内部主键、公开conversation_uuid、order_id、window_id、customer_id、last_seq、last_content、last_message_at、created_at；order_id与公开UUID分别唯一 |
| chat_messages | 内部主键、公开message_uuid、conversation_id、seq、sender_id、sender_side、client_message_id、content、created_at；(conversation_id,seq)唯一；(conversation_id,sender_id,client_message_id)唯一 |
| chat_read_state | conversation_id、user_id、last_read_seq、updated_at；(conversation_id,user_id)唯一，阅读进度只增不减 |
| chat_event_outbox | 事件UUID、会话UUID引用、投递时间、次数、下次尝试时间、创建时间；与消息同事务写入，避免入库后进程退出而完全没有提示 |

公开接口不返回内部用户/消息/会话主键；身份使用用户UUID，会话和消息使用公开UUID。seq仅为会话内顺序与阅读水位，不是公开用户账号。正文不放Redis，也不写普通请求日志。

会话创建靠订单唯一约束兜底并发。发送事务锁定会话行，先查幂等记录，再递增last_seq并写消息、摘要及outbox；序号更新随事务一起回滚。相同幂等键同内容返回原消息，不同内容报冲突。已提交请求的重试即使订单刚关闭，也应在当前仍有读取权限的前提下返回原结果，不重新插入。

列表按COALESCE(last_message_at,created_at)与唯一标识形成稳定游标，默认20条、最大50条；创建后没有消息的会话也必须可见，双方都能在各自授权的通知中心找到它。历史按seq取最近30条、最大50条。对历史用beforeSeq，对断线补拉用afterSeq，二者互斥，跨多页补齐后再合并实时消息。未读计算统计阅读水位之后的对方消息，不能简单last_seq减last_read_seq（会把自己的消息计为未读）。

## 五、通信协议与可靠性

### 复用一条连接

继续使用现有 /notifications/socket-ticket 与 /notifications/ws，不另建每订单Socket。既有 notification.changed 保留原语义，不让每条聊天消息都触发订单刷新。用户端补一个明确的类型分发层，订单订阅只接收订单通知变化，聊天订阅只接收聊天事件。

现有票据身份未保存聊天角色，不能直接信任客户端传来的角色；新增消息处理必须重新确认当前身份、角色和窗口权限。连接建立时不自动订阅全窗口消息，先按会话授权订阅；每次收发和补查再次验证，撤权后不再推送正文。

### 拟定消息帧

```json
{"type":"chat.send","requestId":"本次请求UUID","conversationUuid":"会话UUID","clientMessageId":"客户端消息UUID","content":"请问还需要多久？"}
```

服务端本地事务提交后返回 chat.ack，包含requestId、conversationUuid和完整message对象；message含clientMessageId、messageUuid、seq与createdAt。在线设备只收到chat.changed与conversationUuid，再由HTTP授权补拉正文，避免广播正文及维护第二套正文合并协议。ACK与补查可能乱序，客户端以messageUuid去重，并用clientMessageId替换本人发送中占位。

失败返回 chat.error，携带requestId、稳定错误码和可展示提示，不回显令牌或内部异常。帧大小、文本长度、JSON结构和未知事件类型都在服务端校验。发送ACK代表已持久化，不代表对方在线、收到或已读。

### 离线与多实例

消息和outbox同事务提交 → 后台发布轻量消息引用 → Redis Pub/Sub分发到各实例 → 目标实例复核接收者权限后发送WebSocket。复用并扩展现有通知转发基础，Redis操作通过common-redis封装；重试和轮询属于outbox投递，不扫描全部聊天正文。

Redis Pub/Sub不保存离线消息，离线订阅者会漏掉提示。因此它只承担实时转发，持久记录、游标补拉和未读查询负责恢复。outbox投递成功也不代表所有客户端已收到。客户端重连时触发补查，可见聊天页每30秒兜底查询；客户端重连、回前台和进入会话时主动补查，恢复不依赖重发所有历史正文。

首期不要求每条聊天再经过RocketMQ：订单状态通知继续沿用现有MQ链路，聊天在通知服务内完成本地事务与实时推送，不引入Seata全局事务。若后续新增独立审核、客服或离线推送消费者，再评估由outbox发布MQ事件。

复用当前会话串行发送保护、发送时限、缓冲限制与过期清理；新增心跳、连接上限和消息限流时复用已有公共能力。退出登录、凭据版本变化、权限撤销、账号切换均清理订阅和未发送草稿。权限查询失败时停止向该连接发送聊天正文。

## 六、HTTP接口草案

以下契约已实现于源码；服务加载新代码后可调用。统一响应、分页和错误码沿用项目规范。

| 方法与路径（经网关加/api） | 作用 |
| --- | --- |
| POST /chat/conversations | body仅订单标识；校验后获取或创建会话 |
| GET /chat/conversations?cursor=...&size=20 | 本人可访问的商家/顾客会话摘要 |
| GET /chat/conversations/{uuid} | 会话详情、订单摘要与当前canSend；服务端实时决定 |
| GET /chat/conversations/{uuid}/messages?beforeSeq=...&size=30 | 首屏和向上翻页 |
| GET /chat/conversations/{uuid}/messages?afterSeq=...&size=30 | 断线缺口补拉，支持连续分页 |
| POST /chat/conversations/{uuid}/read | body为lastReadSeq，验证存在、归属和范围后单调更新 |
| GET /chat/unread-count | 本人聊天未读总数；与系统通知总数合并展示tabbar红点 |

发送走WebSocket，历史与已读走HTTP；首期不另做重复的HTTP发送入口。连接不可用时保留重试状态，不悄悄改用另一条发送链路。商家会话列表先按当前授权窗口约束查询，不先取所有人的聊天再在内存过滤；窗口集合应批量获取，避免每行一次远程权限请求。

## 七、关键权限边界

- 顾客只读写本人订单的会话；每个UUID/游标都不能替代鉴权。
- 店主必须具有该窗口当前有效经营授权。私有资源不存在与越权采用一致结果，避免枚举。
- 创建与发送从订单服务确认真实状态/归属/窗口；现有订单通知事件可作提示，不作为唯一授权依据。
- 读取历史同样检查当前访问权；撤权后的旧店主不能因曾发送消息就永久保留入口。
- 通用权限缓存存在有效期，聊天不能承诺“撤权立即生效”却仅读过期缓存；实施时核验主动失效与订阅清理，必要时关键收发回源验证。确认失败即拒绝，不默认放行。
- 订单状态与本地聊天事务无法天然原子：规则建议以发送时订单服务授权检查为准，允许检查通过后极短时间内订单转终态。若要求终态提交后严格零新消息，需要额外跨服务协调，应先明确代价。
- Nginx、Gateway同步WS升级与超时，生产使用HTTPS/WSS；长期Token不放URL，短期票据不进日志，日志不打印聊天正文。
