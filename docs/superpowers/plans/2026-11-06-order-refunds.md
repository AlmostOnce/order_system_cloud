# 任务7：按菜品退款与售后实施计划

**Goal:** 学生按订单菜品及数量申请退款，未接单直接退回余额并回库存；已接单商家审批，拒绝后可升级经理，72小时未处理自动同意。

**Architecture:** 退款单放在订单模块，单笔对应一个订单明细和数量；订单行锁协调接单/退款，菜品计数限制累计数量。批准后退款单充当持久化执行任务，后台有界扫描，调用支付/用户幂等退款和库存幂等部分回补，失败重试而不虚报成功，不用跨服务长事务。沿用MP的model/mapper/service/impl/controller/dto/vo分层。

**Tech Stack:** MySQL、本地事务、既有Feign、库存/通知Outbox、uni-app x。

## 已确认规则及具体边界

- 已支付即未接单，平台自动同意并回库存；和商家接单同时竞争，按数据库当前状态决定分支。
- 制作中/待取货由商家审批并决定是否回库存；已完成自首次完成时间起72小时可申请且不回库存。
- 商家收到申请后72小时未处理自动同意；已接单超时自动退款不自动回库存，避免恢复已制作餐品。经理介入保持独立队列，不虚构经理超时自动审批规则。
- 单项按数量退款，金额由订单实付快照计算，客户端不传金额；支持同一菜品分次退款，处理中/待审批数量占用申请额度但不暂停制作。
- 商家拒绝后学生可申请介入。食堂经理按既有食堂/窗口授权范围，总经理全平台；技术管理员无审批入口。
- 整单履约数量全部退完则不能继续制作/核销；未完成订单进入已退款，已完成订单保留完成状态及评价历史。部分退款不影响其他菜品，明细返回剩余履约数量。
- 本项目学生余额渠道实际扣款才可退余额，不能把MOCK渠道记录凭空变成余额。
- 本次不改变“已支付累计销量”排行榜统计口径。商家审批只提供后端接口，不写uni-app管理页。
