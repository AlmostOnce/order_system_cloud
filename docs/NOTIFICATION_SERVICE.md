# 站内通知服务实施方案

## 首期范围

面向已登录顾客提供订单状态变化通知，支持通知列表、未读数、标记已读和 WebSocket 实时推送。断线或离线时，以数据库通知列表为事实来源，重新连接后通过列表和未读数补齐；不接入短信或邮件。通知只反映已经成功提交的状态变更，不影响下单、支付和库存的业务判定。

## 可靠投递

1. 订单服务在订单状态及版本更新的同一事务中写入 `order_notification_outbox`。事件包含版本、稳定的事件标识、订单编号、订单版本、接收用户内部编号与目标状态。事务回滚时事件也回滚；重复状态更新不生成新事件。
2. 后台发布器读取待发送事件，同步确认 RocketMQ 接收后标记已发送；超时或异常保留记录并退避重试。崩溃导致重复发送是允许的。
3. 通知服务验证事件、在 MySQL 写入 `notifications`，以接收用户和事件标识的唯一约束实现幂等。写入成功或已存在才能确认消费；数据库失败要抛出错误以触发消息重试。异常消息按既有 MQ 策略进入死信，不静默丢弃。
4. 数据库提交后向该用户在线会话推送轻量通知；推送失败不删除记录，不将 WebSocket 发送成功当成用户已读。每个账号可有多个设备连接，重连时重新查列表。

## 身份与接口约束

HTTP 接口及 WebSocket 握手必须验证 JWT 签名、签发方、过期时间与注销黑名单，并将公开用户身份解析为内部用户编号。服务端只使用认证结果决定接收人，禁止客户端指定其他用户 ID。WebSocket 握手不得把长期访问令牌写入 URL 或日志；跨浏览器与 uni-app x 的握手认证方式须与现有网关能力一起验证，不能仅依赖浏览器无法自定义的握手头。

列表和未读数按当前用户隔离；游标使用公开通知标识，后台按内部顺序分页。标记单条已读时同时限定通知标识和接收人，重复操作幂等；批量已读限制作用域为本人。通知 JSON 不暴露用户内部编号。

## 落地顺序

1. 注册独立服务与必需依赖，接入现有配置、认证、日志与网关路由。
2. 执行数据库迁移，新增订单状态事件事务写入和可靠发布器。
3. 实现通知持久化、幂等消费、列表与已读接口，再实现认证后的 WebSocket 推送。
4. 将通知中心和未读标记接入用户端，并验证断线重连、跨用户隔离、重复消息、服务重启和失败重试。

当前进度：已准备通知服务启动类、JWT 认证配置、本人通知列表/未读数/已读接口、订单状态事件幂等落库和 MQ 消费配置源码，以及订单侧事件、outbox 写入组件和发布器；已注册服务模块和依赖。本机数据库已创建 `notification_db.notifications`、`order_db.order_notification_outbox` 及通知数据库账号。用户端通知列表和路由草案已补充，但网关 Nacos 配置尚未发布。非取消状态已补充与订单状态同事务写入 outbox 的代码，MQ 出站绑定已配置，但事件开关和消费配置尚未启用；WebSocket 和用户端实时推送尚未完成，服务尚未构建或联调。新增源码尚不可作为已交付功能使用。取消订单属于 Seata 全局事务，不能直接把本地分支提交视为全局提交。

取消通知 TCC 草案已补充 Try、Confirm、Cancel 和 `order_notification_tcc` 表；本机已创建该表。Try 只写预备状态，Confirm 在本地事务中同时更新状态并写入可发布 outbox，Cancel 记录取消状态以防空回滚后的悬挂。通过不使用 Maven 的隔离状态测试；功能开关默认关闭，未进行真实 Seata 回调、数据库事务、故障恢复或 MQ 联调，不应视为可启用的生产实现。
